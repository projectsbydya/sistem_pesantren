# AGENTS.md

Persistent project knowledge for agentic coding tools working in this repo.

## Business Rules

### Assignment / AssignmentMember (class-centric academic assignments)

- `Assignment` is a **snapshot**, not a live template — its data (title, target,
  metadata, etc.) is fixed once created and does not retroactively affect
  already-generated members.
- `AssignmentMember` rows are generated **only once**, at the moment the
  assignment is published (either created directly with `state=published`,
  or via a later `draft` → `published` transition). Creating a `draft`
  assignment never enrolls anyone.
- Students who join a class **after** an assignment has been published are
  **NOT** automatically added to that assignment's roster. The roster is
  fixed at publish time.
- Re-publishing an assignment that has already been enrolled (e.g.
  `archived` → `published` again) does **not** re-sync or re-generate the
  roster — enrollment is idempotent/one-time.
- If manual roster additions are needed later, that must be a deliberate
  future enhancement (e.g. a teacher-facing "add student to assignment"
  action) — there is currently no automatic backfill for late joiners.

### Account provisioning (closed registration system)

- There is **no public self-registration**. `/register`, `/register/pesantren`,
  `/register/santri`, `/register/orang-tua` are all disabled (redirect to
  `/login` or 404) — see `docs/REFACTOR_PRIVATE_SYSTEM.md`.
- **Tenant admin accounts**: created only by Super Admin
  (`TenantManagementController` + `TenantProvisioningService`), which
  auto-generates a secure random password shown once on a credentials page.
- **Ustadz / Santri / Parent accounts**: auto-generated by the tenant admin
  when their data is input (`UstadzController`, `SantriController`,
  `ParentController`, all via `UserProvisioningService`) — never via a
  self-service signup form.
- Do not resurrect `ParentRegistrationController`, `SantriRegistrationController`,
  or `PesantrenRegistrationController` (removed as confirmed dead code) unless
  this business decision changes.

### Repository / git hygiene notes

- `tests/` is intentionally excluded from git (`.gitignore`) as of this
  cleanup — it is not shipped in the pushed repository. Run tests from a
  local/CI copy that still has the `tests/` directory.
- `storage/framework/views/*.php` (compiled Blade cache) must never be
  committed — a `storage/framework/views/.gitignore` (matching the sibling
  `storage/*` folders' `* ` + `!.gitignore` convention) enforces this now.
- Watch for stray files at the repo root with names like `Schedule::...` or
  `->something,` — these come from unescaped `>` in `php artisan tinker`
  one-liners run directly in bash (the shell interprets `>` as redirection).
  Always wrap `tinker --execute="..."` code in quotes and avoid literal `>`
  where possible. `.gitignore` now has `*::*` / `->*` patterns to stop these
  from being accidentally committed again.
- A commit already pushed to `origin/main` (`48b640a`) contains two files at
  the repo root whose *names* leak a real super-admin plaintext password
  (from an unescaped tinker redirect). `.gitignore` cannot retroactively
  scrub committed history — this needs a git history rewrite
  (`git filter-repo`/BFG) plus password rotation for the affected account.
  Treat this as unresolved until explicitly confirmed done.
